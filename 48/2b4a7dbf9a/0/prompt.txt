# Copilot Task: Upgrade New Game Setup Into a Premium Campaign Wizard With Empire Emblems

## Context

Before implementing, inspect the existing repository.

The current New Game setup screen lives at:

```text
crates/game_tui/src/screens/new_game_setup.rs
```

Current behavior:

- It renders a single `GALAXY CONFIGURATION` panel.
- It uses `compose_layout(...)` and `render_footer(...)`.
- It reads setup state from `AppState::new_game_setup`.
- It uses `Theme` styles.
- It imports empire definitions via `game_core::all_empire_definitions()`.
- Empire selection currently happens elsewhere; this screen shows the chosen empire as a read-only header.
- Editable setup fields currently include:
  - galaxy size
  - AI empire count
  - seed
- It shows derived values:
  - stars
  - sectors
  - difficulty hardcoded as `Standard`
  - victory enabled/disabled summary
- Tests already exist for:
  - render without panic
  - selected empire name
  - alternate empire cursor
  - galaxy size label
  - AI count
  - seed
  - derived summary
  - wide panel sizing
  - active field highlight
  - specific empire descriptions
  - enter hint behavior

Do not assume a blank slate.

Refactor carefully around the existing state, tests, and command/event model.

---

# Goal

Turn the existing New Game setup screen into a polished, production-quality campaign setup experience.

This should feel like:

- founding a civilization
- preparing an interstellar campaign
- initializing a galactic expedition
- using a premium terminal command deck

It should NOT feel like:

- a debug form
- a raw config panel
- a generic ncurses menu
- a temporary prototype screen

---

# Important Architecture Rules

Respect existing architecture.

Do not couple UI rendering directly to game simulation.

Do not mutate game state from rendering code.

Input handling should continue through the existing app flow.

Preserve the clean separation:

```text
game_core  = headless simulation / definitions / deterministic logic
game_tui   = rendering, screen state, keyboard UX
game_save  = persistence
content    = data/templates where applicable
```

Use existing structures where practical:

```rust
AppState::new_game_setup
Screen::NewGameSetup
Theme
compose_layout
render_footer
all_empire_definitions()
GalaxySize
VictorySettings
VictoryPath
```

Avoid large rewrites unless necessary.

# Add Empire Emblems

The New Game setup should show an emblem for the selected empire.

The emblem is appropriate here even though it was removed from the splash screen.

Reason:

- splash screen should stay clean
- campaign setup is where empire identity belongs
- the player should feel they are choosing/founding a civilization

---

# Emblem Design Goals

Empire emblems should feel like:

- command insignia
- galactic seals
- fleet standards
- civilization markers

They should NOT feel like:

- emoji
- fantasy heraldry
- random ASCII noise
- debug placeholders
- clip art

Preferred glyph language:

```text
◈ ◆ ◇ ▲ ▼ ▣ ▢ ▤ ╱ ╲ │ ─
█ ▓ ▒ ░ ▀ ▄
```

Avoid emoji for core layout.

---

# Emblem Implementation Direction

Create reusable emblem rendering infrastructure.

Recommended location:

```text
crates/game_tui/src/components/emblem.rs
```

or:

```text
crates/game_tui/src/widgets/emblem.rs
```

Use whichever module structure best matches the existing repo.

Suggested type:

```rust
pub struct EmpireEmblem {
    pub pattern: EmblemPattern,
    pub primary: Color,
    pub secondary: Color,
    pub accent: Color,
}
```

Suggested enum:

```rust
pub enum EmblemPattern {
    Frontier,
    Citadel,
    Eclipse,
    Nexus,
    Obelisk,
    Helix,
    Dominion,
}
```

Start with handcrafted patterns.

Do not implement procedural random generation yet.

The renderer should support compact sizes:

```text
5x5
7x7
9x9
```

Start with one reliable size if needed, but keep the API extensible.

# How To Map Emblems To Empires

Use stable deterministic mapping initially.

For example:

```rust
let pattern = EmblemPattern::from_empire_index(empire_idx);
let palette = EmpireEmblemPalette::from_empire_index(empire_idx);
```

This avoids needing to change `game_core` definitions immediately.

Do not block on adding emblem data to core content unless that is already easy.

Future work can move emblem identity into data/content.
